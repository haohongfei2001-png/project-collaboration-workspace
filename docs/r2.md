## 事件怎样成为可查看的进展

GitHub App 的签名事件经专用入口到达 `POST /api/webhooks/github`。只有原始字节签名、投递 ID 和载荷验证通过，数据库事务完成后，接口才返回 `accepted: true`。重复投递保留原记录；相同投递 ID 携带不同内容会拒绝。

事件先作为事实保存，再排入同步任务。同步使用当前安装范围的只读 token，补读 PR、评论、代码差异、Actions、检查、部署及选定计划/状态文件。每次读取有请求数、页数、时长和正文上限；未读完时保存续读游标，覆盖不足不会伪装成“没有变化”。来源缺失、权限撤销、限流和读取失败都有单独状态。

失败投递另由 App 身份查询 GitHub 投递记录，按已绑定安装和项目范围请求有限次数重投。GitHub 返回 202 只记为“已请求重投”，只有本地收到并持久化同一 delivery 才记为恢复。GitHub.com 的记录及重投窗口是三天；超窗、重试耗尽、上游显示成功却没有本地回执都会保留不完整状态。REST 补读不能完整恢复从未送达、已经超过重投窗口且随后删除的短暂记录。详见 [恢复操作与来源限制](r2-operations.md#webhook-失败投递恢复)。

分析任务读取项目当前 generation、开发线 SHA、相关新事实、关键资料及此前判断。调用前在数据库中锁定并预留预算；同一项目 generation 和模型配置版本的自动分析只预留一次。已发送但结果不确定的付费调用不会悄悄自动重试。成功结果与费用结算在同一个事务保存；过期版本只能进入历史。前端每 30 秒在页面可见且已登录时读取后台已保存状态；前端轮询不是监控调度器。

后台周期由 [运行手册](r2-operations.md) 中的五分钟调度驱动。`waitUntil` 和请求后的即时 worker 仅用于减少延迟，不能替代独立定时器。

## AI 判断的产品边界

输出包含 `stage`、`progress`、`completed`、`incomplete`、`failed`、`blockers`、`pendingVerification`、`userActions`、`nextSteps`、`changeReason` 和 `resolvedIssues`。每条判断区分事实、推断、未知和建议，并关联输入证据 ID；URL、完整 SHA 和时间由服务端从证据记录补入，模型不能自行发明来源字段。

检查成功只证明对应检查；合并和部署不等于产品验收。计划范围不完整时百分比保持未知。旧问题未明确解决时会带入下一轮，模型不能通过省略或改放“已完成”来清除。不同 SHA、同 SHA 不同验证范围、历史失败和成功重试分别保留。

普通开发讨论不会自动变成审批。用户事项必须有可信作者、当前明确请求和原文精确引用，并通过否定、历史引用、过期来源检查。首次较长回填自动最多生成一次明确标记的部分分析，来源尚未完整复核时禁止生成 `userActions`；续读每一页不会各自触发付费分析。个人处理记录只改变工作台的待办展示，不改变来源事实。自然语言 gate 保持保守，可能漏掉表达不明确的请求；真实模型质量和节省用户时间的程度仍须用 [同源比较](ai-evaluation.md) 证明。

输入上下文有界，并优先保留未解决引用、关键计划/状态文档、可信讨论和当前检查。完整原记录继续留在数据库。上下文删减、正文截断、未完整读取和前轮摘要均向模型和界面披露；这不是全量仓库知识索引。

## 数据与权限

数据库使用独立的 `pcw` schema，001 核心迁移与 002 投递恢复迁移共为 22 张表启用并强制 RLS。迁移入口依次执行版本化 SQL，再检查全部表、运行角色和不可变记录权限。运行连接切换为 `pcw_app`，该角色无超级用户或 `BYPASSRLS` 权限。用户查询在事务中绑定 `pcw.user_id`；服务端 worker 使用专门的事务作用域。GitHub 与模型凭据采用 AES-256-GCM 加密，并绑定用户/资源上下文。应用不向浏览器返回数据库连接、加密密钥、GitHub token 或模型 Key。

RLS 是服务端数据隔离的第二道防线。运行数据库凭据具有切换服务端作用域的能力，因此必须留在服务器；不允许把 `pcw` 加进 Supabase 的公开 Data API schema，也不授予 `anon` 或 `authenticated` 直接访问。证据、审计和个人处理记录对运行角色禁止 UPDATE/DELETE。资料和待办允许用户编辑，每次修改同时保存为不可变的 `workspace_record` 证据版本，进入后续分析的关键资料选择；任务勾选只是个人记录，不能成为产品验收。

当前只开放 `PCW_OWNER_GITHUB_ID` 指定的个人账户；不提供组织或多人协作产品。会话使用 HttpOnly cookie，写操作检查 Origin 和 CSRF。Vercel 预览维持 SSO 保护；GitHub 和定时器通过各自认证的窄入口桥接，不能为 Webhook 关闭整站保护。

## 成本与恢复

每个模型连接独立设定月预算和币种，按 UTC 月界记账；不做隐含汇率转换。输入/输出单价由用户按自己的计费条件填写，不预置猜测价格。预算为零或缺少有效价格时停止调用。预留使用保守输入估算和总输出 token 上限；失败和超时不默认免费，实际用量缺失时保留估算。费用记录保存调用时模型和价格快照；这不是服务商账单的替代品。

重复同步不重复保存相同事实；重复分析由 generation、provider 版本和 retry key 去重。异常任务有限次退避，失效租约不能写入新结果。用户可在修复密钥、预算或服务故障后手动重新分析；该操作重新检查预算并产生新的显式重试记录。没有活跃模型时 GitHub 事实仍可持续保存，项目显示等待分析。

## 原型及历史的保留

`/` 是 R2 的服务端工作台。`/watch-v1.html` 保留上一版公开读取原型及原浏览器存储；`/personal-v1.html` 和 `/legacy.html` 保留更早版本。构建继续生成三个历史独立 HTML；R2 本身需要同源后端，不能把独立 HTML 当作 R2 持续监控服务。

旧产品说明及验证记录见 [Watch V1](watch-v1.md) 与 [完整验证历史](verification.md)。没有创建第二套竞争路线，也没有把旧快照自动写进新的服务器项目列表。

## 个人实测证据入口

当前问题旁的“记录验证”将用户自报结果保存为不可变证据。服务端要求当前分析的 generation 与 SHA 一致、绑定一个未解决问题，并校验实际环境、场景范围、观察事实及两项本人确认；一个表单的网络重试复用同一幂等键。该记录不会改变 GitHub 审批、合并或部署。通过只允许关闭对应问题，不能推导整体产品可用；失败、同时间冲突、新版本及更晚验证会触发复核。旧问题、原分析和原验收依据均留在历史中。
