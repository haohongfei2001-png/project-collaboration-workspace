# 个人第一版：每天打开，知道产品到了哪里

2026-10-31（北京时间）· 方向修订

本稿取代 R1 中“先服务跨角色团队”的优先级。R1 的版本、依赖和证据规则可以继续使用，团队管理界面不再决定首页。本文是产品规格；实际实现、真实连接与模拟范围以 README 和验证记录为准。

## 当前实现

个人界面已支持项目、功能卡片、待办、随手记、个人关注问题保存和实际体验确认；功能进度由本版范围、关联开发状态及对应版本的个人确认共同决定。项目回答目前采用规则生成，**没有接入大模型**，不能宣称已理解任意源码或笔记。

GitHub 已接入真实公开仓库只读 API，覆盖最近更新的 100 个 PR 和最近 30 次 Actions 运行，不读取源码，也不代表全部检查或完整仓库历史。用户可手动同步；开启自动同步后，在页面可见、当前没有弹窗或详情操作时，按至少五分钟的间隔检查当前项目。关闭页面不继续工作；私有仓库授权和后台持续同步尚未实现。读取失败保留上次状态并提示，不能据此声称项目没有变化。

项目和个人关注保存在当前浏览器。现有版本可以演示持续状态与可追溯的进度，但“比一次高质量 GPT 问答更有用”仍须通过真实日用比较验证。

## 1. 首先服务一个正在做产品的人

第一位用户是同时推进若干软件项目的独立产品创作者。他可能让 AI 编写代码，也可能自己开发；不一定熟悉分支、检查、发布等工程术语。他需要知道产品能不能用、为什么还不能用，以及现在值得做什么。

核心价值定义为：**持续把 GitHub 中的变化转成自己看得懂、能追溯、能行动的产品状态。**

GitHub 保留工程事实，工作台组织个人目标及其实现情况。超过 GitHub 的目标限定在“理解和推进自己的产品”，不承诺重做更强的代码托管服务。

相比每次向 GPT 问“项目怎么样了”，工作台必须多做四件事：记住本版目标；自动更新；突出上次看过之后的有效变化；把判断留在可操作的功能卡片里。不能仅将同一段问答改为卡片排版，也不能无证据宣称模型推理更强。

## 2. 首屏只回答三个问题

1. **现在能用到什么程度？** 一句产品结论，配本版功能进度。
2. **和上次相比有什么值得我知道？** 仅呈现影响产品使用的变化。
3. **下一步做什么？** 最多三项，优先显示用户能够采取的动作。

例如：“反馈录入和分类已做好；提醒还有一处失败，完整流程暂时不能确认。先试一次从录入到收到提醒。”点击后才展开相关检查与来源。

没有变化时保持安静；没有充分证据时说明“尚未确认”。不能把同步失败说成项目没有进展，也不能把没有新提交说成开发者没有工作。

## 3. 卡片是对象，图标帮助识别

默认回到上次打开的项目；“我的项目”中每个项目是一张卡片：图标、名称、一句话状态、本版进度及需要处理的标记。进入项目后保留稳定的“概览、功能、资料”入口；待办由功能和阻塞产生，不另建一套需要重复维护的管理系统。

概览包含一张主状态卡、当前关注的功能卡片、必要的下一步。功能卡统一结构：图标与名称、当前能做什么、状态、一个主要动作。卡片展开后才显示实现细节、资料、代码来源和记录。不能把每一个字段都包成卡片，也不把整张卡做成含糊的多重点击区。

图标与短标签配合：加号表示创建，箭头表示进入，勾表示确认完成；图标不承担未经学习便难以辨认的专业含义。桌面和手机保留相同对象与称呼，手机收起侧栏，功能卡片保留紧凑排列，详情全屏打开。

首页移除成员头像堆叠、角色切换、审计流水、验收队列、连接商标条和方法论解释。多人协作留待后续加入；记录放入“查看依据”或详情中的“记录”。来源正常时安静显示同步时间，只有过期、失败或撤权才提示处理。

## 4. 进度围绕功能，不围绕忙碌程度

用户先确定本版希望做到的功能，例如“录入反馈、分类整理、更新处理状态、发送提醒”。AI 可以建议功能及其代码关联，初次映射需要确认；不能随意从 PR 标题生成分母。

每项功能保留产品完成条件，并显示：未开始、开发中、待实测、已确认可用。阻塞作为附加原因，信息不足作为证据状态，不把它们混成进度百分比。

主进度条显示本版已确认可用的功能数；其余部分可区分待实测和开发中。文字写“2 / 4 项可用，1 项待实测”，不写模糊的“开发完成 75%”。不同功能的工作量并不相同，这个比例表示本版能力覆盖，不预测剩余工时。

PR 合并支持“实现已进入目标分支”；CI 成功只支持被执行检查通过；部署成功支持相应环境存在可访问版本。它们都不能单独证明功能实际可用。真实体验确认必须对应具体版本；影响该功能的新修改出现时，保留历史确认并提示当前版本待确认。新增、取消功能会明确改变本版范围。

## 5. AI 自动工作，用户按需追问

正常流程是同步后自动刷新产品卡片，而非要求用户先进入聊天窗口。摘要先给结论与影响，再给下一步；PR、SHA、日志属于展开层。用户可继续问“为什么”“我现在能试什么”“还有什么挡住发布”。

AI 需要区分代码事实、产品推断与个人确认。每条重要判断有可打开的依据及观察时间；不同来源冲突时明确指出，不能综合成假确定结论。用户可纠正“这个功能并没有完成”，纠正应持续生效并可复核，不能下一次同步又被旧推断覆盖。

个人关注点可以固定，如“我什么时候能自己日用”“发布前还差什么”。默认使用这些关注点组织卡片；没有必要先要求填写复杂偏好表。

本地模拟、真实只读同步、真实模型分析必须明确区分。首次真实版优先只读，不自动合并 PR、不发布、不修改仓库。后台同步需要服务端凭证和调度，浏览器内定时刷新不能冒充关闭页面后仍工作的服务。

## 6. 先验证日用价值，再增加协作

第一轮验证用自己的真实项目：每天打开一次，检查能否快速正确回答“能用什么、卡在哪里、该做什么”。同时记录哪些结论错误、过期、重复，以及是否仍须重新把背景复制给 GPT。

与一次高推理问答比较时，使用相同可访问来源和同一版本，不依靠不同信息量制造优势。比较结论正确性、下一步可执行性、理解耗时与重复准备成本。暂不设定未经观测的效率提升比例。

只有个人持续使用后，再加入共享项目、责任分配和评审。多人能力应沿用同一套功能卡和依据，不让用户从个人工作台迁入另一套企业管理产品。

校招展示重点是这次取舍：从完整功能集合回到首位用户的日常任务，建立可信的产品进度与持续上下文，并通过真实复演和比较验证价值。页面数、测试数和自动生成的文字量不能替代使用证据。

## 7. 当前实现与后续架构

当前是无第三方运行时依赖的静态浏览器应用。`personal.js` 负责界面和操作；`personal-domain.js` 用纯函数维护项目、功能、任务、笔记、体验确认与来源投影；`github-sync.js` 只负责公开读取和归一化。浏览器存储是个人记录的持久层，GitHub 是开发事实来源；两者不互相覆盖。内置 `github-snapshot.js` 是带时间戳的实际读取基线，首次联网成功后由新快照替换。

| 阶段 | 最需要实现的内容 | 验证门槛 |
| --- | --- | --- |
| 当前个人原型 | 卡片、个人目标、真实公开读取、对应版本的体验确认、下一步、资料与规则说明 | 自己的项目能完成创建、同步、理解、行动、复核的闭环 |
| 下一步个人可用版 | 在明确授权范围读取 README、需求与必要代码差异；模型生成带证据的产品解释；用户纠正与来源版本持久保存 | 同一项目、同一来源与高质量 GPT 问答比较，判断准确、理解容易、减少重复准备且不遗漏阻塞 |
| 持续同步与备份 | 最小权限 GitHub App、服务端事件接收与队列、去重和定期校准、用户身份与隔离、备份恢复 | 页面关闭后仍可靠更新；撤权后停止读取；旧来源不被当成当前事实 |
| 经日用验证后的协作 | 在同一功能对象上加入共享、负责人、评审及权限；服务端逐请求鉴权 | 不让个人使用增加管理步骤，跨用户访问与 AI 代理操作能够被系统拒绝和追溯 |

模型不能直接把推断写成“已可用”。事实读取、产品推断、个人确认应分别存储，模型回答带来源标识、版本与读取时间；引用过期或代码版本变化时重新评估。初期模型只读并提出建议，修改目标或范围由用户确认。尚不需要实时协同编辑、全量代码索引、复杂贡献网络或完整企业后台。
