# Project Collaboration Workspace｜校招展示与真实验证方案

版本：R1 · 2026-10-31（北京时间）

## 1. 作品需要让招聘方记住什么

**这是一项将模糊协作愿景收敛为可执行工作流的产品作品。**它展示的不只是页面，而是对任务、资料、外部事实、采用决定、验收和 AI 权限的独立判断。

建议标题：

> Project Collaboration Workspace：面向小型软件团队的项目执行与成果验收工作台

一句话介绍：

> 将项目任务、资料版本、设计方案、GitHub 实现证据和验收决定关联起来，帮助人和 AI 在同一份可追溯的项目上下文中推进工作。

当前阶段应标为**高保真可交互原型**。浏览器内操作产生真实状态变化；GitHub、Drive、AI 和角色身份采用模拟。没有真实团队规模、用户增长、商业营收或生产效率提升数据。

当前已提供空白项目与反馈闭环模板两种起点；支持手工登记示例资料、正式提交候选方案、采用和验收。三个里程碑与成员角色固定。完整外部事件和 AI 规划使用内置反馈需求；AI 草案支持完整预览、整份批准或放弃，不支持内联修改、部分批准或对任意新需求进行真实语义拆分。后续设计中的自定义里程碑、成员管理、方案完整版本编辑和正式请求修改流程，不能写进本轮已完成清单。

## 2. 三类岗位分别看什么

| 岗位 | 重点展示的能力 | 最有说服力的页面或证据 |
| --- | --- | --- |
| AI 产品经理 | 判断 AI 是否必要；上下文组织；来源引用；权限边界；从建议到受控操作 | 问题回答及可点击来源、变更草案、不同权限角色、失败/未知情况 |
| B 端软件产品经理 | 角色责任、状态规则、信息架构、流程闭环、低切换成本 | 项目概览、任务详情、方案比较、验收与交付队列 |
| 技术型产品经理 | 事实来源、跨系统同步、模型边界、版本冲突、可测的命令契约 | 外部来源更新、采用版本保持、合并与验收分离、技术架构和测试记录 |

不应把“独立完成大量代码”作为唯一重点。招聘方更需要知道为什么这样定义问题、为什么放弃其他功能、设计如何被验证，以及哪些能力仍未实现。

## 3. 竞争理解：避免容易被追问击穿的表述

不能写“现有工具无法让 AI 理解整个项目”或“没有工具把 GitHub 和项目管理结合”。

- [Linear Agent](https://linear.app/docs/linear-agent)已经支持基于工作区数据回答问题和执行工作对象操作。
- [Linear GitHub integration](https://linear.app/docs/github-integration)已经关联 PR/commit 并自动更新任务状态。
- [Linear Releases](https://linear.app/docs/releases)明确区分 PR 合并与进入发布环境。
- [Notion AI Connectors](https://www.notion.com/help/notion-ai-connectors)已经进行跨来源检索、引用和权限映射。
- [GitHub Projects](https://docs.github.com/en/issues/planning-and-tracking-with-projects/learning-about-projects/about-projects)已经直接连接 Issue/PR 并提供多种项目视图。

更准确的表述是：

> 在成熟工具已具备任务、集成和 AI 能力的前提下，我选择了一个更窄的工作问题：小型团队如何共同确认当前采用的成果版本、实际实现证据和验收状态，并在来源变化时保持判断可追溯。

这是一项待验证的工作流设计，不是已被证明的市场独占能力。也需要验证独立工作台是否值得引入；若维护成本过大，集成层或插件可能更合理。

## 4. 五分钟演示脚本

演示项目始终为 **客户反馈闭环 / FB**。林澈为产品负责人，沈言为设计师，周屿和陈序分别负责前后端，许宁负责测试和交付，顾乔为观察者。不要在不同页面临时更换团队、任务或项目。

演示前明确一句：**这是浏览器内可操作的产品原型，外部同步和 AI 已标为模拟。**

五分钟是讲解版节奏，不是所有任务从零执行完毕的承诺。建议预先建立一个反馈闭环模板项目，在同一项目中完成必要前置工作，并如实说明当前所处阶段；保留一项待验收工作用于现场闭环。若现场触发 Drive 更新或批准新增任务，必须额外完成受影响任务的资料复核和验收，不能直接跳到交付。完整从零演练应按实际操作用时进行。

| 时间 | 操作 | 讲解重点 | 应看到的状态变化 |
| --- | --- | --- | --- |
| 0:00–0:40 | 打开项目概览，定位目标、当前里程碑和一项待处理问题 | 首次进入便能理解目标、责任和下一步，首页不靠统计卡片堆砌 | 进入与该问题关联的任务或证据 |
| 0:40–1:20 | 打开任务展示负责人、资料和前置关系；从零演练时再创建、指派任务 | 一条任务包含执行依据和交付要求，不只是标题与截止日 | 列表、详情和负责人视角保持一致 |
| 1:20–2:00 | 比较沈言提交的方案 A/B，采用确定版本并记录理由 | 候选方案、版本和采用决定分别建模；未采用方案保留 | 当前采用关系和决策历史变化 |
| 2:00–2:40 | 模拟 GitHub PR 合并，再模拟 Drive 资料更新 | 合并提供实现证据；新文件版本不自动改写已采用依据 | 任务进入待验收或更新实现证据；新版待确认提示出现 |
| 2:40–3:30 | 询问 AI 当前阻塞，点击引用；生成并检查草案；完整演练时批准写入 | AI 共享项目上下文，但回答有范围、写入有审查 | 引用跳到对应对象；完整预览显示验收条件、日期和来源；获批任务进入同一工作结构 |
| 3:30–4:15 | 切换观察者或只读 AI，尝试受限操作 | 权限需要在行为层验证；前端模拟仍不是生产安全边界 | 写入被拒绝或不可执行，并解释具体原因 |
| 4:15–5:00 | 许宁核对一项任务的标准和证据；仅在全部门槛已满足时确认交付，否则展示剩余门槛 | 最终进度由任务、成果和验收事实组成 | 进度与活动记录更新；完成全程后交付证据可以回溯 |

如果现场时间有限，优先保留“版本冲突 + PR 合并未验收 + AI 引用”三个判断点，少演示普通导航。

不要使用一键自动完成所有步骤来代替主要操作。可以提供恢复演示初始状态，但应说明它只重置本地示例数据。

还可单独展示“空白项目 → 新任务 → 资料登记 → 两个候选方案正式提交 → 采用 → 验收”的人工闭环。空白项目不应因为登记了文档就宣称获得真实 AI 语义能力；这是与模板演示不同、边界明确的路径。

## 5. 八页作品集结构

| 页 | 要回答的问题 | 建议材料 |
| --- | --- | --- |
| 1 | 解决什么问题，为谁解决？ | 小团队角色、分散工具、一个具体交接/验收困境 |
| 2 | 为什么不是再做一个任务看板？ | 竞争事实、独立价值假设、明确排除的功能 |
| 3 | 如何从原始理念收敛？ | 保留接力/多方案/采用/贡献，排除公开市场/交易/权益 |
| 4 | 数据为什么这样组织？ | 工作分解、依赖、版本、引用、采用的清楚区别 |
| 5 | 用户如何完成工作？ | 同一任务从要求到资料、候选方案、PR、验收的连续截图 |
| 6 | AI 为什么有用，如何约束？ | 有来源的回答、覆盖边界、可审核变更、角色差异 |
| 7 | 如何证明不是假按钮？ | 实际构建、交互测试、状态变化与响应式证据；清楚标模拟 |
| 8 | 哪些结论仍未得到验证？ | 用户验证计划、独立工具维护成本、下一阶段优先项 |

最终作品集应使用实际运行截图。设计说明、需求合同和测试计划不得冒充已完成的实测记录。

## 6. 工程验证与用户研究分开报告

### 6.1 工程验证

本期可以真实验证的是代码和原型行为：任务创建/指派/状态变化，资料关联，采用指向精确版本，重复操作的处理，权限命令拒绝，模拟事件处理，刷新持久化和响应式布局。

报告应列出执行命令、环境、日期、测试范围和实际结果。测试未运行、浏览器未检查或某路径只人工检查时都应明确。不能因为单元测试通过，就写成真实 API 同步可靠；不能因为模拟角色被拒绝，就写成生产鉴权安全。

### 6.2 用户研究

用户研究回答的是人是否理解并愿意使用产品，工程测试不能替代它。以下为**计划，尚未执行**。

招募 6–8 名有协作经验的参与者，覆盖产品、设计、工程、测试/交付。记录其工具经验，避免全部来自同一专业或同一团队。参与者数量用于发现问题和形成初步方向，不足以推断市场整体效率。

### 6.3 对照方法

准备两组内容难度相近的虚构项目资料，分别放在“文档 + 任务表 + GitHub 示例页面”与原型中。交替安排使用顺序，避免所有人先做基线再做原型造成学习偏差。

每位参与者完成以下任务：

1. 说出项目目标、下一里程碑、当前最大阻塞和责任人。
2. 在外部最新版本与项目采用版本不同时，找到当前实现依据。
3. 判断一个已合并但未验收的 PR 是否代表项目可交付。
4. 比较方案并完成采用，找到采用理由。
5. 核对 AI 回答的证据，并拒绝一项证据不足的建议。

主持人先观察，不提前教操作。发生困难后记录位置，再给予帮助。取得参与者同意后才录屏或保留可识别个人的信息。

### 6.4 记录指标

| 指标 | 记录方法 | 不应做的解读 |
| --- | --- | --- |
| 正确完成率 | 为每项任务提前定义可观察的正确答案 | 不用单次正确点击证明长期工作有效 |
| 完成用时 | 从任务说明结束至正确完成；求助单独标记 | 不把小样本实验直接换算为公司节省人力 |
| 错误类型 | 版本混淆、把合并当验收、找错责任人、引用误读等 | 不只报告总体满意度掩盖关键错误 |
| 求助与回退 | 记录次数及触发环节 | 不把“第一次不会用”都归因于用户习惯 |
| 证据核查行为 | 是否点开引用、检查版本和更新时间 | 不把对 AI 的主观信任当作回答正确性 |
| 重复维护负担 | 记录两套系统中必须重复输入的字段和步骤 | 不忽略新增工具的成本 |
| 参与者原话 | 取得许可后保留匿名原话与上下文 | 不把个别正面评价作为市场需求证明 |

### 6.5 预先设定的产品目标

以下仅是下一轮参考目标，**不是本项目已达到的数据**：

- 至少 6/8 名参与者能在 90 秒内找到当前正式依据及其采用理由。
- 关键任务中没有参与者将“PR 已合并”直接判断为“验收完成”。
- 与对照场景相比，正确率不降低，关键判断的中位用时有所改善；可将 25% 作为值得继续投入的探索性参考。
- 多数参与者可以在不依赖主持人解释的情况下完成采用及验收。

即使目标通过，也只形成小样本初步证据。若结果失败，优先调整概念命名、对象关系和任务上下文，不急着增加更多功能。

## 7. AI 专项验证计划

建立小型固定评估集，至少覆盖：正常资料、过期版本、外部失去授权、缺少验收、多个候选方案、互相冲突来源，以及资料中包含要求绕过权限的文本。

每例预先给出允许访问的对象、期望引用版本、可得结论、不得执行的动作和需要承认的不确定性。分别检查事实准确性、引用对应性、权限边界、写入预览和重复执行。

确定性模拟可以验证交互与操作合同，不能证明真实模型质量。接入真实模型后，需要重新执行评估，并记录模型版本、输入范围和失败样例。模型不应凭空填满“未知”的格子。

## 8. 简历表达

只有在实际完成交互、构建及对应检查后，才使用与事实相符的版本：

> 独立定义并设计面向小型软件团队的项目协作工作台，贯通任务、GitHub PR、资料版本、方案采用与验收流程；实现可交互原型及角色权限、来源引用、同步事件演示，建立可解释的项目进展模型，并完成主要交互与响应式验证。

如果简历只有两行，优先突出个人判断和实际产物：

> 将跨领域协作构想收敛为团队项目执行场景，设计工作分解、依赖、成果版本和采用/验收模型；实现浏览器交互原型，演示跨来源更新、受限 AI 建议与可追溯交付。

AI 相关技术可以写“设计授权上下文、来源引用、审核后写入和审计机制；原型采用确定性模拟”。没有接入模型时，不写“完成 RAG 系统”“实现自主 AI Agent”。

未发生真实研究前，不写真实用户数、效率提升、满意度、收入、留存或企业使用成果。测试数量和通过率只能引用最终实际记录，不能从计划中推算。

## 9. 面试追问准备

### 为什么需要 AI？

人在任务、文档、PR 和决策之间重建上下文的成本高。AI 可以将被允许访问的事实组织成摘要和下一步草案。项目状态和权限由确定性规则负责，AI 不应独自决定是否验收通过。

### 为什么不直接用 Linear 或 Notion？

它们已经能完成大量相关工作。本作品探索更明确的跨角色成果采用和验收流程是否能降低理解成本。当前不能证明用户一定需要一个独立产品；下一阶段会比较实际判断效率及额外维护成本。

### 树状结构为什么没有画成一张大图？

任务从属、前后依赖和成果版本不是同一种关系。把它们都画成树会误导用户。日常操作使用层级列表和上下文关系，只有解释复杂依赖时才需要图。

### 如何避免 AI 读取无权资料？

生产系统在服务端验证用户、项目与外部来源权限，再检索资料；执行写入时重新校验。前端隐藏内容和提示词都不能构成安全边界。原型只是可执行的角色规则演示。

### PR 合并后为什么还没完成？

合并是代码事实，验收是对业务要求和指定成果的确认。实现证据可以推动进入待验收，但不能自动证明设计、测试、权限或交付条件已满足。

### 现在最需要开发什么？

先验证采用版本、任务上下文和验收流程是否让真实团队更容易判断。获得证据后，优先建设可信身份/授权与持久化，再以受控范围接入 GitHub 只读事实和用户显式选择的 Drive 资料，最后接入可评估的真实 AI。不要先建全部后端再寻找使用价值。

## 10. 下一阶段的最小真实验证

选择一个愿意试用的小团队和一个明确的两周项目，只接入一个代码仓库、一个资料范围及少量交付任务。先不开放任意外部写入，让工作台记录采用和验收，验证其是否在真实交接中被持续使用。

重点观察：成员是否主动从任务查看资料；负责人是否用采用/验收记录作出决定；来源更新是否能正确触发复核；AI 的引用是否被核查；是否新增了难以承受的维护工作。

这些证据将决定本项目下一步是继续独立产品、收缩为集成层，还是调整目标用户。能根据事实改变产品方向，也是作品中应展示的产品能力。
