# Watch V1：个人项目工作台

2026-11-01（Asia/Shanghai）。本稿接续个人优先方向，取代上一版宽卡片、单项目主状态卡占据首页的组织方式。实际验证结论见 [verification.md](verification.md)，不以设计规格代替测试证据。

## 1. 用户每天需要完成的事

首位用户同时推进几个真实软件项目，开发可能分散在多个 AI 对话、PR 与分支中。打开工作台，先找到正在做的项目，看到阶段与计划进展，再判断这一轮有没有结果、哪里没有通过、是否真的需要自己决定。

首页服务快速扫描；进入项目后服务理解与行动。项目介绍不占卡片空间，代码哈希、完整日志和来源原文进入展开层。记录保留完整性，通过“开发历史”和“计划”按需查看。

## 2. 信息结构与视觉选择

| 层级 | 显示内容 | 主要操作 |
| --- | --- | --- |
| 首页 | 应用图标、名字、阶段、当前计划进度、少量提醒 | 打开、关注、搜索、筛选 |
| 开发概况 | 当前结论、所跟进的开发线、检查、这一轮结果、下一步、需关注 | 刷新、处理事项、安排下一步 |
| 开发历史 | 每轮完成、未通过或当时未完成、下一步、来源版本 | 看失败与回退、读新讨论 |
| 计划 | 当前计划和之前计划并排，状态与来源独立保留 | 比较变更、打开确切版本 |
| 资料 | 项目笔记与链接 | 创建、修改、重新找到 |

白色是主要工作表面，浅灰承担边界，蓝色用于主要操作和关注状态，失败与待处理使用少量语义色。桌面以四列紧凑卡片为当前基准；较窄屏幕减少列数，手机保留相同名称与对象，收起侧栏。四列是有效扫描密度的选择，不要求所有尺寸固定四列。

卡片没有介绍段落。图标识别应用，短标签说明阶段，进度条说明登记的计划项；提醒放在卡片底部，关注开关独立于打开项目的点击区。详情页用稳定的四个页签，减少在不同管理模块之间跳转。

## 3. 用真实项目暴露判断问题

初始目录包含八个真实公开项目。来源研究、确切版本和读取时间随数据保存，后续 API 快照可以更新工程事实。

两类实际例子直接影响设计：

- PAIA 的 PR 曾描述 Atelier 17 已发布，随后 main 直接提交了官网回退。开发历史必须保留前后两个事实，并以更新的主线事实说明当前状态。
- TodayAction 同一 Draft 保留多个阶段的结果。较新版本的真实界面到数据库检查成功，不代表旧混合负载失败已经解决；旧段落写“未验证”也不能覆盖新检查证据。

因此，每条事实必须有对象、版本和观察时间；“最近一条 PR 文案”不能独自成为项目真相。历史失败不会被删除，也不会在新版本有明确修复后仍冒充当前阻塞。

三枚应用图标直接来自实际仓库。未找到正式图标的项目使用文字占位，不将它们包装成新品牌资产。研究仓库可以进入同一工作台，但研究能力、工程状态与产品可用性保持不同口径。

## 4. 进度与阶段怎么判断

前台将“开发阶段”“当前计划进度”“检查结果”“需关注”分开：

- **阶段**来自已核对的当前计划或状态说明，保留出处。
- **计划进度**按已收录的计划项显示完成数和状态。只在完整范围明确、状态完整且来源仍有效时，才具备计算该范围百分比的条件。
- **检查结果**只来自对应代码版本的已读取运行；缺失、跳过或覆盖不全不冒充全部通过。
- **需关注**来自明确来源或当前检查信号，表达具体需要处理的对象。

当前八个项目的计划多为摘录，因此展示当前计划计数，不宣称整个产品完成率。HCL 的 10 / 11 也只代表登记工程包，不能当作商业化完成 91%。新增范围会改变分母，代码活动数量与剩余工时不参与伪精确计算。

主线与开发 PR 是可选择的跟进对象。选择 PR 后重新读取其当前 head；没有读到该 PR 时保留未知，不偷偷换成另一条开发线。新的 head、计划正文版本或相关讨论可能使原有产品摘要需要复核，此时旧摘要、计划与阶段保留为历史依据。

## 5. 监控、提醒与处理记录

### 当前真实能力

适配器直接调用公开 GitHub REST API。每轮五个基础读取，按配置最多增加计划、评论两个读取；只保留有界的近期资料。仓库近期评论按更新时间读取，再筛选相关事项，不能把最早一页评论当成最新讨论。读取范围、截断与缺失会写入快照。

关注选择与自动监控开关分开。用户可以只关注当前工作的几个项目；自动读取默认暂停，开启后所有项目共享“每十分钟一个项目”的前台调度。页面关闭或不可见时不继续读取。多个项目的单项目更新间隔随关注数量增长；这不是关闭页面后的实时后台监控。公开额度不足时停止扩大发送并等待恢复，读取失败保留先前结果。

### 什么会产生提醒

| 依据 | 当前处理 |
| --- | --- |
| 所选代码版本的检查失败 | 标记当前检查未通过，并提供运行链接 |
| GitHub 明确的阻塞标签 | 生成阻塞事项 |
| 明确的待批准 / 待决定标签 | 进入相应事项类别 |
| 经核对的来源记录了具体问题 | 保留来源与版本；新证据到来时要求复核 |
| 新评论或计划更新 | 展示新原文与来源变化，不擅自生成确定的产品结论 |
| 没有新提交、PR 为 Draft | 不据此判定卡住或等用户批准 |

“记下处理结果”是个人工作台的本地记录，不是 GitHub 审批或自动修复。它只对应当时的来源事项；来源或代码版本变化会重新产生需要核对的提醒。完整操作记录收在历史内，避免每天重复展示已处理信息。

### AI 边界

本版没有接入模型，也不读取任意源码。已核对的产品结论来自本次资料整理，自动新增的 PR、提交和检查记录使用事实级表达。任意评论中的“批准”“失败”等词不会被关键词扫描直接变成当前审批要求。

要实现用户期待的智能监控，必须进一步判断讨论是在回顾历史、请求当前动作、已经解决还是被新计划替代；这需要版本化上下文和模型质量验证。仅增加一个聊天入口或把 PR 标题改写成中文不足以完成这个目标。

## 6. 当前技术结构

| 组件 | 职责 |
| --- | --- |
| `data/*-evidence.json` | 已核对的公开项目资料、历史结果和来源 |
| `compose-watch-data.mjs` | 生成统一项目目录，嵌入实际图标，不生成虚构进度 |
| `watch-domain.js` | 版本对应、计划进度、检查状态、提醒、历史与本地处理记录 |
| `watch-sync.js` | 公开只读请求、归一化、限流信息与覆盖范围 |
| `watch.js` / `watch.css` | 卡片与项目详情、关注调度、个人资料及待办 |
| 浏览器存储 | 个人关注、快照、笔记、待办与处理记录 |
| 构建脚本 | 静态站点和无外部脚本 / 样式依赖的独立 HTML |

GitHub 保存开发事实；工作台保存个人关注与整理后的投影，二者不互相覆盖。旧的个人版与团队原型保留独立入口和存储，不通过覆盖旧数据完成这次迁移。

跨标签页保存使用当前存储版本检查，冲突或存储错误明确提示。它仍是本地原型，不是多人并发数据库。当前没有跨设备同步、云端备份或 UI 导入恢复。

已观察到的新回合按确切版本归档，后续 API 窗口不再包含旧事件时也保留历史。计划来源不可读时保留上一份正文。新依据一旦使旧结论待复核，不能因下一次没读到该依据而自动恢复。

## 7. 最小可行的下一阶段

后续以同一条数据流推进，无需先建设完整企业后台：

1. **GitHub App 与持续事件接收。** 用户选择仓库和最小只读权限；服务端验证 webhook 签名，保存 delivery ID，按事件去重。定期校准补上漏报，不能将 webhook 当作永不丢失的唯一来源。
2. **版本化事实与权限。** PR、检查、计划与讨论分别保存来源版本、时间、读取状态；撤权后停止读取并处理缓存。项目权限在服务端和检索入口验证，不能只隐藏按钮。
3. **有依据的产品解释。** 在获准范围内读取需求、状态、必要代码差异与讨论；模型分别输出工程事实、产品影响推断和建议。重要判断附来源、版本和不确定性，冲突保留待复核。
4. **需要本人介入的事项。** 将真实阻塞、明确审批和产品取舍分开。模型提出候选，系统复核来源身份、当前版本、既有授权和已处理记录，再决定提醒；初期保持只读。
5. **真实日用比较。** 用相同项目、同一版本与相同可访问来源，对照高质量 GPT 问答。比较遗漏、误报、理解时间、下一步可执行性以及重复准备成本，不编造效率提升。

个人持续使用成立后再加入共享、分工和评审。当前最重要的验证是：白天同时推进几个项目，晚上打开工作台时，能否准确看到每个项目今天真正做成了什么、哪里失败、是否需要自己采取行动。
