# Project Collaboration Workspace｜产品设计与交互合同

> **当前优先级已调整为个人第一版。**默认入口、范围和实际连接能力以 [README](../README.md) 与 [个人版规格](personal-v1.md) 为准。以下正文保留为 **R1 团队协作原型的历史设计**，不作为当前个人版需求；其中团队优先级、模拟同步及旧界面描述只适用于 `legacy.html`。

版本：R1 原型设计 · 2026-10-31（北京时间）

## 1. 本轮要验证的产品

面向同时使用代码仓库、在线文档和文件存储的小型软件团队，提供一个围绕项目目标、任务上下文、成果采用和交付验收组织工作的统一工作台。

它的核心问题是：**负责人知道哪些工作真正推进了项目，成员知道当前依据什么、下一步做什么，AI 也只能依据被允许访问的同一套事实提出建议。**

本轮交付是浏览器内运行的高保真交互原型。任务操作、资料关联、方案采用、状态推导等在浏览器内产生真实状态变化；GitHub、Drive、AI 输出和不同身份均采用明确标识的演示数据及模拟行为。它不代表已经连接真实外部 API，不代表生产系统已具备可信鉴权、多人并发、模型推理或持久化服务。

### 1.1 原始理念的继承与收敛

来源为作者提供的[原始想法文档](https://docs.google.com/document/d/1N0Xws1JlBWhPQCbPNz2-znh6bK4_s1aj/edit)。本轮已读取该来源；链接对应的实际文件为 Word 文档。为保护原始资料，本仓库不复制其全文。

保留四项有价值的思想：工作可以继续发展；同一工作可以产生不同成果；负责人采用某项成果后，它才成为正式进展；未采用的成果及贡献者仍被保留。

把这些思想收敛为团队内部的日常工作：需求依据、责任分配、方案评审、代码实现、验收与交付。公开发现、跨领域创作市场、商业交易、权益分配、版权争议和最终品牌均不在本期范围。

GitHub 初始核查基线：`main` 为 `bd7ec9a9d1947b7f1390ef40285053db8da7ff3d`，初始仓库仅有 README。该 SHA 是开始时的依据，不应作为后续远端当前状态的保证。

### 1.2 首批用户及使用时刻

首批目标是大约 5–15 人、跨产品/设计/工程/测试协作的软件团队。这是待验证的用户假设，不是已获取客户规模。

| 角色 | 经常遇到的判断 | 工作台需要提供的帮助 |
| --- | --- | --- |
| 产品或项目负责人 | 为什么还不能交付？谁需要决定什么？ | 阻塞原因、采用依据、待验收队列和下一责任人 |
| 设计师 | 当前采用哪个方案？变更理由是什么？ | 候选方案比较、明确版本、评审决定和历史保留 |
| 前后端工程师 | 依据哪个需求版本实现？PR 合并后还差什么？ | 任务内的依据、依赖、外部实现记录和验收要求 |
| 测试或交付负责人 | 验收对象是什么？结果能否追溯？ | 精确成果版本、标准、实现证据和验收记录 |
| 新成员或观察者 | 项目在做什么、当前为什么这样做？ | 可访问范围内的项目摘要和决策来源 |
| AI 助手 | 哪些事实有效？能采取哪些操作？ | 授权上下文、版本及来源、操作草案和审计链 |

高价值时刻优先选择：进入新项目、交接任务、等待决策、需求版本变化、PR 合并后验收、准备交付。初期不追求替代成员全天使用的代码编辑器、文件编辑器或即时通信工具。

### 1.3 R1 已实现范围与后续设计的区别

本文同时记录产品目标和交互合同，不是“文中所有能力均已实现”的声明。当前原型的操作边界如下，实际构建及浏览器验证以最终测试记录为准。

| 能力 | R1 可操作范围 | 后续能力，不计入本轮完成 |
| --- | --- | --- |
| 项目建立 | 创建空白项目或客户反馈闭环模板，填写名称、目标和交付日期，切换已建项目 | 项目设置的完整编辑、成员邀请、真实多人空间 |
| 里程碑 | 使用需求对齐、设计与实现、验收与交付三个固定阶段，给任务选择阶段 | 自定义里程碑、增删阶段、时间线规划 |
| 任务组织 | 创建、指派、填写验收条件、建立前置依赖、编辑任务要求/上级/日期、提交及验收；普通父项显示子项汇总 | 完整的依赖/验收条件编辑器、任务取消/归档、范围基线管理；被其他任务等待验收的交付任务不可直接改成分组 |
| 项目资料 | 手动登记示例快照、读取允许范围内的正文、关联任务和固定版本；内置来源可模拟更新与撤权 | 真实文件上传、外部 API 连接、任意资料的连续版本编辑、完整文件管理 |
| 候选成果 | 任务负责人正式提交独立候选方案，绑定已有资料版本；按任务比较、采用，保留备选及决定 | 同一逻辑方案的完整多版本编辑器、逐条评审评论、正式请求修改/拒绝工作流 |
| AI 草案 | 内置反馈需求生成确定性任务草案，展示完整拟写入内容，负责人整份批准或放弃 | 草案内联编辑、部分批准、任意手工需求的语义拆分、真实模型推理 |
| 角色与历史 | 固定演示团队、角色切换、领域命令校验、事件与决策记录、负责人完整示例导出 | 修改角色策略、邀请/移除成员、不可抵赖审计、高级历史筛选 |

空白项目支持人工登记资料、提交候选成果、采用和验收；完整的 GitHub/Drive 事件及 AI 规划演示使用内置反馈闭环模板。手工快照不由内置同步脚本覆盖，规则规划器也不会冒充已经理解任意手工需求。

### 2.2 本期的差异化假设

**把跨角色的交付证据组织起来，比继续增加一个功能入口更有价值。**

从任务出发，用户能依次回答：需求来自哪里，候选成果有什么不同，采用了哪个版本，谁做出了什么决定，实现关联哪些 PR，是否达到验收标准，以及最终交付包含什么。

这个假设有三个具体结果期待，尚待用户验证：

1. 更少误把最新草稿当正式依据。
2. 更少误把代码合并当任务验收完成。
3. 更快找到当前阻塞、证据和应当推动它的人。

工作台增加一套维护负担也是真实风险。若核心对象仍需在两处重复维护，或用户判断时仍必须打开所有原工具，本产品形态需要收缩为既有工具的集成层或插件。

## 3. 六项核心产品判断

### 3.1 首页首先服务判断和推进

首页按“项目目标 → 当前阶段和交付状态 → 需要当前用户处理的事 → 相关证据”组织。成员数量、文件数量、活动数量不占据主要视觉层级。

下一步行动应有完整语境，例如“设计方案等待林澈采用，影响前端任务”，而不是只有“3 项待处理”。

### 3.2 将组织、依赖、版本和采用分别建模

阶段/模块/任务的从属结构可以是树；任务依赖是有向关系；文件和方案版本是演化记录；文档引用是多对多关系；采用是指向具体版本的业务决定。用户不需要学习图论，但模型必须避免把这些关系混成一张树。

### 3.3 进度必须可以解释

优先展示“已验收 / 本轮纳入范围”“待验收”“受阻”的组成。若出现百分比，只对纳入范围的叶子交付任务计算，避免父子任务重复计数，并明确它衡量的是验收覆盖率，不是剩余工时。

任务拆分、增减范围会改变分母，应记录范围变化。没有足够实际历史时，不预测交付日期，不生成貌似精确的风险分数。Linear 的[项目进度图](https://linear.app/docs/project-graph)也将范围、进行中和已完成分别呈现；本期更应优先做好可解释的事实。

### 3.4 资源以用途和关联呈现

资料库不只是文件夹的镜像。资源需要说明它是需求依据、参考资料、候选成果还是验收证据，关联哪些任务，采用哪个版本，外部来源最近何时变化。

### 3.5 AI 位于工作上下文中

AI 在当前项目或任务侧边获取上下文，不要求用户重新复制背景。回答中提供可打开的来源；写入先形成变更草案。未知、过期和无权限内容不能用自然语言推测填补。

### 3.6 采用、验收与交付有各自责任

采用决定“项目接下来以哪个成果为依据”；验收决定“该任务的成果是否满足要求”；交付决定“本轮约定范围是否已具备完整的可交付证据”。三者有不同对象、操作和记录。

## 4. 信息架构与导航

### 4.1 一级导航

| 入口 | 用户问题 | 主体内容 | 主要操作 |
| --- | --- | --- | --- |
| 概览 | 项目在做什么，当前最需要我推动什么？ | 目标、范围、里程碑、交付状态、阻塞、待办 | 进入待办、查看证据、询问 AI |
| 工作结构 | 工作如何组织，谁承担什么？ | 按里程碑/模块组织的任务及其状态、负责人、依赖 | 创建、拆分、指派、调整状态、打开详情 |
| 资料库 | 当前工作的依据是什么，哪些来源更新了？ | 有来源身份的资源、用途、版本、关联任务、访问状态 | 关联任务、检查版本、查看源内容 |
| 成果与验收 | 哪些结果需要决定或确认？ | 待决策成果、待验收任务、本轮交付清单 | 提交候选成果、比较、采用、验收、交付；正式请求修改后续实现 |
| 进展记录 | 发生了什么，为什么这样变化？ | 人工操作、同步事件、采用决定、AI 写入、验收记录 | 查看记录并回到关联任务；高级筛选后续实现 |

成员与权限、连接设置位于导航下区。它们不抢占日常工作视线，但必须可发现、可解释。

### 4.2 详情采用上下文面板

任务打开后保持原列表或概览位置。面板包括任务要求、负责人、验收标准、阻塞关系、资料、PR 和候选成果入口；相关历史在进展记录中核查。每个区块只展示当前任务所需内容；详细源记录可以进一步展开。

默认只打开一个主要右侧面板。任务详情与 AI 使用清楚的切换或相互跳转，不默认同时占用两列。桌面中等宽度时优先保证主体任务名称、负责人和状态可读，手机用全屏详情与明确返回路径。

### 4.3 “成果与验收”中的三个工作队列

这是本设计最大的认知风险点：若将所有结果都称为“成果”，用户会分不清下一步。

应通过对象名称和主操作加以区分：

| 队列 | 对象 | 主操作 | 结果 |
| --- | --- | --- | --- |
| 待决策 | 候选方案的具体版本 | 比较并采用 | 新的采用决定 |
| 待验收 | 已提交任务及其证据 | R1 验收通过；后续加入正式请求修改 | 验收记录与任务状态变化 |
| 本轮交付 | 已约定范围和交付清单 | 完成交付 | 锁定本轮交付证据的记录 |

不使用一个通用“完成”按钮承担上述所有语义。

## 5. 实体及关系合同

下表是领域语义，不要求实现为同名数据库表；具体工程结构以代码和技术架构文件为准。

| 实体 | 身份与核心内容 | 重要约束 |
| --- | --- | --- |
| 项目 | 持久 ID、目标、范围、负责人、状态 | 项目目标和范围不靠任务标题推测 |
| 里程碑 | 项目内阶段或可验证结果、计划日期 | 进度来自纳入范围的工作；阶段不等同于文件夹 |
| 工作项 | 任务 ID、父任务、负责人、要求、验收标准、状态 | 从属关系不得成环；父节点不与叶任务重复计入完成分母 |
| 依赖 | 前置任务、后续任务、阻塞理由 | 与从属关系分离；初期拒绝依赖环 |
| 外部资源 | provider、外部 ID、URL、类型、同步与访问状态 | 外部 ID 才是身份；文件名和路径变化不制造新资源 |
| 资源版本 | 资源 ID、来源版本或快照标识、作者、观察时间 | 不把所有来源的版本号当成同一种语义；外部缺乏稳定修订标识时需说明证据限度 |
| 候选方案 | 所属任务、贡献者、说明、若干版本 | 多个方案可以并存，不等同于 Git 分支 |
| 方案版本 | 内容或外部证据引用、贡献者、提交时间 | 正式提交的内容不能无痕修改 |
| 采用决定 | 采用的方案版本、决策人、理由、时间 | 指向具体版本；新决定保留旧决定；不默认验收其他任务 |
| 验收记录 | 任务、成果版本、标准、证据、验收人、结果 | 审核对象确定；权限独立验证；修改请求也需留痕 |
| 交付记录 | 本轮范围、被确认的任务和成果、交付人 | 缺少必需验收时不能显示为完整交付 |
| 成员/AI 身份 | 人或代理、角色、项目权限、授权范围 | AI 不能仅凭提示词获得额外权限 |
| 审计事件 | actor、动作、对象、时间、来源、变更摘要 | 人工、同步和 AI 产生的事件均可区分；不把审计记录当聊天消息 |

### 5.1 关系不混用

- 工作分解：项目中的阶段/模块/任务形成从属结构。
- 工作依赖：任务之间形成有向依赖关系，允许一个任务依赖多个任务。
- 版本演化：同一候选成果包含版本记录，必要时记录其来源版本。
- 资料引用：资源可以关联多个任务，每次关联说明用途。
- 正式采用：决定指向具体成果版本，承担“为什么目前以它为准”的业务含义。

初期不必提供通用关系图编辑器。清楚的列表、层级缩进、依赖区块和引用跳转足以表达多数真实工作。

## 6. 状态与进展规则

### 6.1 任务状态

任务可从未开始进入进行中，随后提交待验收，最终由有权人员确认验收完成。阻塞作为可解释的工作条件展示；实现可将其建模为状态或推导字段，但必须保留具体阻塞原因和解除条件。

目标流程中，需要修改时回到可继续工作的状态，同时保留上一轮验收意见。R1 可由有权成员重新调整任务状态，正式的“请求修改/拒绝”意见流尚未实现。取消或移出本轮范围同样属于后续能力，不能在本轮演示中把它们宣称为已实现，也不能悄悄当作完成。

### 6.2 外部事实与业务判断

| 事件 | 可自动变化的内容 | 不能自动替代的判断 |
| --- | --- | --- |
| PR 新建或进入评审 | PR 外部状态、任务的实现证据、活动记录 | 业务方案采用、验收通过 |
| PR 合并 | 已实现证据、待验收提示；符合规则时任务进入待验收 | 项目已交付、用户可用、验收标准全部满足 |
| Drive 更新 | 当前来源版本、更新时间、受影响关联提示 | 更改已采用版本、抹去旧决定 |
| 采用新方案版本 | 当前采用指针、新决策记录、受影响任务提示 | 自动完成所有实现或验收任务 |
| 验收通过 | 任务验收状态、里程碑及项目组成 | 未在本次验收范围内的其他工作 |
| 外部失去授权 | 可访问状态与相关判断的不确定性 | 把最近缓存当作当前可授权使用的事实 |

原型模拟同步仅用于展示这些状态规则。生产产品必须重新核实 provider 的权限、版本和同步契约。

### 6.3 可解释的整体状态

整体状态结合里程碑、任务验收、未解除阻塞和资料新鲜度显示。不能只依赖成员手填百分比，也不能仅统计提交数或消息数。

项目显示“有风险”时，应可以打开其依据；如果来源缺失或同步中断，应显示信息不足。工作台不根据缺少事件擅自断言成员没有工作。

## 7. 统一演示项目

### 7.1 项目设定

项目：**客户反馈闭环**，代号 **FB**。

团队正在开发一个小型软件功能，将客户反馈提交、分类指派、处理状态和结果确认连接起来。本期不把原型工作台自身和该演示项目混为同一个产品。

目标：让团队能够把一条反馈从接收推进到有责任人、有处理结果和可确认结论的闭环。演示中的业务效果是目标设定，不是已观测到的客户收益。

三个里程碑：需求对齐、设计与实现、验收与交付。

| 成员 | 角色 | 演示责任 |
| --- | --- | --- |
| 林澈 | 产品负责人 | 确认目标与范围、分配任务、采用方案、作出交付决定 |
| 沈言 | 设计师 | 提交两个候选方案、更新设计成果、回应评审 |
| 周屿 | 前端工程师 | 实现界面、关联 PR、提交验收 |
| 陈序 | 后端工程师 | 实现接口及权限约束、提供实现证据 |
| 许宁 | 测试/交付负责人 | 检查标准和证据、验收、记录缺口 |
| 顾乔 | 观察者 | 在允许范围内阅读，无法修改或验收 |
| 观察 AI | 只读助手 | 基于可访问事实总结、引用和解释 |
| 规划 AI | 草案助手 | 产生任务拆分建议及变更草案，按批准范围执行 |

人物及项目数据均为统一的虚构演示数据，不代表真实团队、真实客户或真实线上事件。

### 7.2 端到端流程

1. 林澈确定项目目标和本轮范围，创建项目并使用三个固定里程碑；完整模拟演示选择反馈闭环模板。
2. 团队关联需求和参考资料，说明它们的用途及来源身份。
3. 林澈将工作拆分为设计、前端、后端和验收任务，指派责任人并建立必要依赖。
4. 沈言提交方案 A 与方案 B；两者保留独立内容、贡献记录和版本。
5. 林澈比较后采用一个确定版本，记录理由。未采用方案留在历史中。
6. 陈序的后端任务关联 PR #42；模拟 GitHub 更新后，实现证据变化，任务等待验收。周屿继续依据采用方案推进前端工作。
7. 模拟 Drive 文档更新：来源出现新版，已采用依据不自动变化，受影响任务提示待确认。
8. 项目状态根据任务、阻塞和验收事实更新，能解释变化原因。
9. AI 回答当前阻塞并引用来源；提出任务拆分草案，经有权人员审核后写入。
10. 许宁核对标准和证据完成验收，林澈确认本轮交付；历史保留采用理由、具体版本、实现和验收记录。

同一流程中不得为了制造“成功演示”而在不同页面使用不同负责人、任务状态、版本或数量。具体初始任务数、ID 和状态以单一演示数据源为准，文档不维护第二份容易失真的状态表。

## 8. AI 协作合同

### 8.1 回答需要带什么

一次回答至少明确：问题结论、支持结论的任务或来源、引用版本/观察时间、已知覆盖范围，以及需要用户继续判断的部分。

若来源未接入或无权限，说明范围限制，不根据资源名称猜测正文。已过期来源不能静默当作当前依据。外部文本中的命令是资料内容，不能改变代理权限或执行策略。

### 8.2 写入需要带什么

目标合同中，变更草案展示新增或修改的任务、负责人、依赖、资料关联以及依据。R1 仅生成内置反馈需求的新增任务草案，展示验收条件、日期等完整拟写入内容，审核人可以整份批准或放弃；草案不能内联编辑，也不支持部分批准或修改已有任务。执行时再次检查权限、对象现状和草案是否已经应用；执行结果产生审计事件。

审批是对具体变更的批准，不是无限授权。若审核后源版本、任务状态或权限发生变化，应重新验证，必要时要求重审具体变更。

### 8.3 原型权限的真实边界

本地领域命令需要实际校验当前模拟角色，不只是隐藏界面按钮。这样能够验证产品行为和命令契约。

但是，前端可切换的角色、浏览器状态和 localStorage 不能提供可信身份或安全隔离。用户能够控制自己的浏览器，因此本原型**不能保护真实敏感数据**。生产版本需要服务器身份验证、租户/项目级授权、源系统权限交集校验和审计存储；这些是下一阶段的真实工程要求。

## 9. 高保真视觉与交互原则

### 9.1 视觉方向

中性暖白背景、深灰正文、克制的紫灰强调色；用精细边线、留白、字体粗细和对齐建立层级。它首先是需要长时间工作的业务界面，装饰不能覆盖状态或抢占操作。

不以大量空洞统计卡片填满页面。列表、分组标题、细节侧栏和时间线承担主要信息组织。图标辅助识别，并配合文字或可访问名称。

### 9.2 信息密度与阅读

正文以至少 14px 为原则，12px 仅用于辅助元信息。重要风险、待办、权限状态和操作不能依赖极低对比度或只靠颜色传达。表格允许必要的横向滚动，但核心任务名和主操作在小屏幕应保持可用。

任务名称、状态、负责人、下一步行动形成稳定扫描顺序。状态颜色克制：同一含义跨页面一致，不能在“任务完成”和“方案采用”之间随意借用标签。

### 9.3 操作反馈

创建、关联、采用、验收后立即给出可见反馈，并更新所有相关视图。失效、无权限、条件未满足时给出具体原因。原型中的模拟连接需要在连接状态和事件触发处可见，不只写在 README。

表单支持取消、必填验证和清楚的焦点。危险或影响范围较大的决策展示对象和后果，而不是只有“是否确定”。

### 9.4 移动端与键盘

移动端导航可收起，详情为可返回的独立层；方案比较可纵向排列。主要操作支持键盘、焦点可见、Escape 关闭临时层，关闭后回到合理焦点。减少动效偏好应被尊重。动效仅解释展开、状态切换或反馈，不制造等待。

## 11. 下一步最值得验证的四个问题

1. 第一次打开项目的负责人能否在短时间内正确找到目标、当前阻塞和下一责任人？
2. 面对“外部最新版本”和“项目采用版本”不同的情况，成员能否选对实现依据？
3. “候选成果 → 采用 → 实现证据 → 验收”是否改善判断，还是增加重复录入？
4. AI 的引用、覆盖范围和变更预览能否帮助用户发现错误，而不只是增加信任外观？

验证方法、演示脚本和校招表达见 [portfolio.md](./portfolio.md)。测试执行结果应以实际测试记录为准，不能用本设计合同替代已完成证据。
